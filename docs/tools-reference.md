# Перелік інструментів

[← Назад до README](README.md)

`mcp-baf` — read-only MCP-сервер: усі інструменти лише читають дані 1С
(`annotations=ToolAnnotations(read_only_hint=True)` у Python SDK 2; `readOnlyHint` у протоколі). Локальні індекси й тимчасові файли будуються на машині MCP-сервера; вихідники користувача не змінюються. Кожен тул повертає готовий **markdown**-текст, а не JSON —
форматування відповіді (заголовки, таблиці, списки) робить сам тул
(`tools/*.py:format_*`), MCP-клієнт показує його як є.

Реєстрація інструментів має стабільний порядок. Максимум — **16**: 13 базових, один з `--dump`, два з `--help-dir`. HTTP-інструменти додатково фільтруються за ефективними правами користувача.

Кожен виклик обгорнутий у `tools/common.py:traced_text`: пише подію аудиту
`tool_call` (успіх, `duration_ms`, `args`) або `tool_error` (виняток
перевикидається далі) і закріплює `trace_id` в contextvar — вкладені
`one_c.http`-події `OneCClient` успадковують той самий `trace_id`.

## Інструменти

| Інструмент | Призначення, параметри, обмеження | 1С / джерело |
|---|---|---|
| `get_metadata_tree` | Дерево метаданих конфігурації: довідники, документи, регістри, переліки, обробки, звіти, загальні модулі та ін. Без параметра `filter` — компактна зведена таблиця (категорія + кількість об'єктів, з підказкою `filter="Категорія"`). З `filter` (рядок, точна назва категорії 1С, напр. `Справочники`, `Документы`, `РегистрыСведений`, `ОбщиеМодули`) — повний перелік об'єктів категорії. Автогенеровані об'єкти з суфіксом `ПрисоединенныеФайлы`/`ПрисоединённыеФайлы` відфільтровуються як шум. Невідомі категорії з відповіді 1С дописуються в кінець (forward compatibility) | GET `/metadata` (`?filter=` передається в 1С, повне дерево кешується на 30 с) |
| `get_object_structure` | Реквізити, табличні частини, виміри, ресурси і типи полів об'єкта метаданих. Для `object_type=Enum` додатково повертається секція **Значення** зі списком значень перелічення. Обидва параметри обов'язкові: `object_type` (`Catalog`, `Document`, `Enum`, `InformationRegister`, `AccumulationRegister`, `AccountingRegister`, `CalculationRegister`, `ChartOfAccounts`, `ChartOfCharacteristicTypes`, `ChartOfCalculationTypes`, `ExchangePlan`, `BusinessProcess`, `Task`, `DataProcessor`, `Report`, `Constant`), `object_name` (ім'я об'єкта, напр. `РеализацияТоваровУслуг`). Тип поля віддається структуровано: `type` (як `Строка(Тип)`), `type_names` (повні імена типів, напр. `Справочник.Номенклатура`), `length`/`precision`/`scale` для примітивів | GET `/object/{object_type}/{object_name}` |
| `execute_query` | Виконати запит мовою запитів 1С і отримати дані (елементи довідника, документи, залишки, обороти тощо). **Лише SELECT/ВЫБРАТЬ**: перше слово запиту після провідних коментарів (`//`, `/* */`) мусить бути `ВЫБРАТЬ` або `SELECT`, інакше `ValueError` до звернення в 1С; той самий гард діє в BSL і в `validate_query`. Параметри: `query` (обов'язковий, підтримує `&Имя`-параметри), `limit` (типово 100, стеля 1000, значення ≤0 замінюється дефолтом), `offset` (0–10000; глибше розширення віддає 400 — пагінація не серверна), `parameters` (словник ключ→значення, ключ без амперсанда). **Дати** в параметрах приймаються в ISO 8601 (`2026-03-01`, `2026-03-01T00:00:00`); зі зміщенням (`Z`, `+02:00`) момент переводиться в місцевий час сеансу 1С, без зміщення — трактується як локальний час. **У відповіді** дати серіалізуються в ISO 8601 (`XMLСтрока`), `NULL` — як JSON `null` (не порожній рядок). Пагінація: `count` — розмір цієї сторінки, `total` — скільки рядків усього (ключ є лише коли результат прочитано до кінця; при `truncated` його немає). Відповідь — markdown-таблиця (`columns`/`rows`), позначка `truncated` і `всего: неизвестно`, якщо результат обрізано; при `--mask-pii` — ще й рядок «замени токенами PII столбцы: …» зі списком замаскованих за іменем колонок (`masked_columns`) | POST `/query` |
| `search_code` | **Реєструється лише якщо задано `--dump`/`mcp_baf_DUMP_DIR`** — без dump-каталогу цей тул взагалі відсутній у списку MCP-тулів (`server.py`: `if index is not None: search_code.register(...)`). Повнотекстовий пошук по коду модулів вивантаження. Три режими (`mode`): `smart` (типово, BM25 + BSL-синоніми ru↔en), `regex` (Python `re`), `exact` (підрядок без урахування регістру). Параметри: `query` (обов'язковий), `limit` (типово 50, стеля 500), `category` (тип метаданих, **чутливо до регістру**, напр. `Документ`, не `документ`), `module` (тип модуля, **чутливо до регістру**, напр. `МодульОбъекта`). До готовності індексу піднімає помилку `search index is building, please retry`; на порожньому dump-каталозі (0 знайдених `.bsl`) повертає текстове пояснення замість помилки. Деталі — [search-and-index.md](search-and-index.md) | Локальний SQLite FTS5-індекс (не жива 1С) |
| `get_form_structure` | Структура керованої форми: елементи, команди, обробники подій. HTTP-ендпоінт 1С у серверному контексті **не віддає** склад елементів і обробники (нема доступу до `ФормаКлиентскогоПриложения`) — тільки ім'я і заголовок (синонім із конфігурації). Порожній склад не маскується під «у форми їх немає»: відповідь містить `elements_available`/`commands_available`, а при `false` — ще й причину (`elements_reason`/`commands_reason`); тул виводить позначку «состав формы недоступен». Повний склад підтягується з `Form.xml` локальної dump-вивантаження, коли сервер запущений з `--dump`; **без dump тул усе одно зареєстрований**, просто повертає лише ім'я/заголовок. Обов'язкові `object_type`, `object_name`; необов'язковий `form_name` — передається в 1С query-параметром `?form=`; невідома форма дає 404 `Form not found` (підміни основною формою немає), без нього береться перша форма за алфавітом серед знайдених у dump. Якщо обидва джерела (HTTP і dump) впали — комбінована помилка з текстом обох причин | GET `/form/{object_type}/{object_name}` (`?form=`) + `Form.xml` з dump (якщо задано) |
| `validate_query` | Перевірка синтаксису запиту 1С **без виконання**. Один обов'язковий параметр `query`. Застосовує той самий SELECT-гард, що `execute_query` (коментар перед `ВЫБРАТЬ` не заважає): не-SELECT запит відхиляється до звернення в 1С, а `/validate-query` повертає `valid=false, errors=["not_select"]`. Відповідь — ✅ «Запрос корректен» (перевірено лише синтаксис; існування таблиць/полів гарантує `execute_query`) або ❌ список помилок з відповіді 1С | POST `/validate-query` |
| `get_event_log` | Читання журналу реєстрації 1С з фільтрацією. Параметри (усі необов'язкові, крім жодного): `start_date`/`end_date` (ISO 8601, напр. `2026-03-01T00:00:00`; зі зміщенням `Z`/`±чч:мм` момент переводиться в місцевий час сеансу), `level` (`Ошибка` \| `Предупреждение` \| `Информация` \| `Примечание`), `user` (ім'я користувача 1С), `limit` (типово 50, стеля 500), `exclude_system` (типово `true`; **лише boolean** — рядок `"false"` дає 400, а не тихе «виключати шум»). Кожен запис виводиться з датою, рівнем, подією, користувачем і за наявності — комп'ютером/метаданими/даними/коментарем/транзакцією. `exclude_system` відсіває транзакційний шум; вікно вигрузки при цьому ширше за `limit` і добирається повторно, тож порожній `events` при живому журналі супроводжується `filtered_empty`. Невідомий `level` — 400, а не «усі рівні» | POST `/eventlog` |
| `get_configuration_info` | Загальна інформація про базу: назва конфігурації, версія, постачальник, версія платформи, режим роботи (`file` → «Файловый», `server` → «Клиент-серверный», `unknown` → «Не удалось определить», якщо `СтрокаСоединенияИнформационнойБазы()` недоступна). Без параметрів | GET `/configuration` |
| `bsl_syntax_help` | Довідка по 180 вбудованих функціях, методах типів (`ТаблицаЗначений`, `Массив`, `Структура`, `Соответствие`, `Запрос` та ін.) і патернах BSL. Працює **повністю локально** — дані з `mcp_baf.bsl._functions_data` (згенеровані з Go-репо скриптом `scripts/gen_bsl_data.py`), без HTTP-запитів і без запущеної 1С. Один параметр `query` — назва функції рос./англ., пошук підрядком без урахування регістру (`СтрНайти` і `StrFind` знаходять один запис). Порожній результат — текстове повідомлення «не знайдена», не помилка | Локальні дані пакета (без 1С) |

## Контракт помилок HTTP-сервісу 1С

Причину відмови клієнт визначає **лише за HTTP-статусом і тілом** `{"error": …, "reason": …}`
(`reason` є не завжди). Окремих заголовків `X-MCP-*`/`X-BAF-*` контракт **не має** і не
використовує: тіло помилки проксі (502/503/504) і тіло відповіді 1С розрізняються статусом,
а `OneCClient` додає до тексту підказку за статусом.

| Статус | Коли | Що робити клієнту |
|---|---|---|
| `200` | Успіх (`ОтветJSON`) | — |
| `400` | Невалідні аргументи, текст запиту, формат дати, `offset > 10000`, не-булевий `exclude_system` | Виправити аргументи |
| `403` | Немає права `Use` на метод, немає права читання об'єкта (`reason=no_read_right`), відмова адмін-прав | Виправити роль HTTP-користувача, не повторювати |
| `404` | Об'єкт метаданих або форма не знайдені | Перевірити ім'я типу/об'єкта |
| `500` | Внутрішній збій розширення (`reason=internal`) | Дивитися журнал реєстрації 1С |
| `502`/`503`/`504` | Шлюз не передав запит | Клієнт повторює автоматично (ідемпотентні виклики) |

Трасування запитів веде `audit.log` (`one_c.http`), а не HTTP-заголовки.


GUID-інструменти `find_object_references` та `get_object_link` приймають типи `Справочник`, `Документ`, `ПланСчетов`, `ПланВидовХарактеристик`, `ПланВидовРасчета`, `ПланОбмена`, `БизнесПроцесс`, `Задача` з точним ім'ям об'єкта після крапки. Порожні GUID відхиляються. Значення переліків цим GUID-контрактом не підтримуються; їх можна переглядати через `get_object_structure`.

| Інструмент | Параметри й поведінка | Джерело даних |
|---|---|---|
| `find_object_references` | `ref` — непорожній GUID; `ref_kind` — повне ім'я, наприклад `Справочник.Контрагенты`. `scope`: `catalogs`, `documents`, `information_registers`, `accumulation_registers`, `accounting_registers`, `calculation_registers`, `all`; типово перші чотири. `limit_hits=200` (1–1000), `limit_per_meta=20` (1–100), `timeout_budget_sec=30` (1–120). Групування за метаданими, ключі записів регістрів, причини пропусків і позначка неповноти. Бюджет перевіряється між запитами; поточний запит не переривається. Результат обмежено правами/RLS | POST `/refs` |
| `get_object_link` | `mode=make`: `ref` + `kind`; `mode=resolve`: `link` — розширення 1С саме розбирає внутрішнє `e1cib/data/Тип.Ім’я?ref=...` (або URL публікації з таким фрагментом); якщо клієнт уже розібрав посилання й передав `kind`+`ref`, вони використовуються як є. Повертає тип, GUID, представлення і внутрішнє посилання поточної бази. Інші схеми й посилання на поля/рядки ТЧ відхиляються; зовнішні URL не завантажуються. Відмова прав на читання об'єкта — `403` + `reason=no_read_right`, а не `400` | POST `/object-link` |
| `get_metadata_rights` | `metadata_object=Тип.Ім’я`; `user_name=""`, `rights=[]`, `roles=[]`. Без фільтрів — типові права поточного HTTP-користувача. Інший користувач/ролі потребують адміністративних прав. За одночасного `user_name` і `roles` перевіряються вказані ролі, про що є примітка. Недоступна перевірка позначається окремо; RLS не аналізується | POST `/metadata-rights` |
| `search_platform_help` | `query`, `limit=10` (1–50), `section=""`: `functions`, `types`, `operators`, `vtables`, `skd`. BM25, двомовні назви, фрагменти сторінок та версія джерела. Розділ визначається евристично; порожній фільтр шукає всюди | Локальні HBK, `--help-dir` |
| `get_platform_element` | `name` — точна назва або мовний синонім; `source=""` — уточнення джерела з результату пошуку, якщо є однакові назви. Повна картка або список кандидатів; невідоме ім'я повертає пов'язані результати пошуку | Локальні HBK, `--help-dir` |
| `bsl_analyze` | `src` — текст до 2 MiB; `levels` типово `error`, `warning` (також `information`, `hint`); `diagnostic_codes=[]`; `limit=50` (1–500). Зведення, коди, позиції від 1, повідомлення. Десять базових перевірок; без контексту всієї конфігурації, не компілятор | Вбудований Python, завжди |
| `bsl_format` | `src` — текст до 2 MiB. Відступи по 4 пробіли та кінцеві пробіли; токени зберігаються. Вихідні файли та база не змінюються. Форматування блокує лише `ParseError` | Вбудований Python, завжди |

Значення лімітів поза діапазоном відхиляються до виконання інструмента. Усі нові інструменти — `readOnlyHint=True`, відповіді — Markdown. BSL-код, представлення об'єктів і результати пошуку не записуються в аргументи аудиту.

Діагностику заповнення/проведення документів відкладено. Джерела реалізації та ідей — [sources.md](sources.md), приклади локальних інструментів — [local-tools.md](local-tools.md).

## Маскування ПДн (`--mask-pii`) — семантика токенів

Концепції перейнято з рецензії vladimir-kharin/1c_mcp v1.10.0 (#44), код не переноситься.

- **Що маскується.** Колонки за іменем: вбудований список `PII_COLUMN_MARKERS`
  (ПІБ/ІПН/РНОКПП, телефон, email, паспорт, адреса, дата народження **+**
  ознаки секретів і боргових ідентифікаторів: `Пароль`, `Логин`, `Токен`,
  `ИмяПользователя`, `Password`, `Login`, `Token`, `СНИЛС`, `НомерКарты`,
  `ЛицевойСчет`, `Серия`, `Номер`, `КемВыдан`) і телефони/email за regex у
  вільному тексті. Доповнення — `--pii-column-markers` /
  `mcp_baf_PII_COLUMN_MARKERS` (список через кому); контракт `/query` не змінюється.
- **Токени.** `PII:xxxxxxxx` — уривок HMAC-SHA256 від значення на стабільному
  32-байтному ключі: файл `<cache-dir>/pii.key` (створюється при першому
  використанні, режим 0600) або `mcp_baf_PII_KEY` (64 hex-символи, старший за
  файл; некоректне значення — помилка запуску, а не тихий фолбек). Токен
  стабільний у межах ключа: **рівні значення дають рівні токени**, навіть
  між рестартами й сесіями; відновити значення без ключа не можна.
  `--rotate-pii-key` випускає новий ключ — старі та нові токени не пов'язані.
- **Документовані винятки та надлишкове маскування.** ПІБ у полі `Наименование`
  (фізособи-контрагенти); ідентифікатороподібні токени (GUID, e1cib-посилання,
  артикули); **голий 10-значний цифровий прогін, що починається з `0`**
  (`0123456789`), маскується як телефон — свідоме надлишкове маскування:
  голі `0671234567` у коментарях 1С — реальний канал витоку, тож вимагати
  роздільники/префікс не можна.
- **Помилки 1С.** При `--mask-pii` агент отримує фіксовану фразу замість
  тексту помилки (regex не гарантовано викидає ПІБ/адреси з довільного
  тексту); повний текст пишеться в `audit.log` подією `pii.error_text`
  ([logging-and-audit.md](logging-and-audit.md)).
- **Дескрипції інструментів** `execute_query`, `get_event_log`,
  `get_form_structure`, `search_code` містять цю семантику токенів; у
  відповіді `execute_query` — перелік замаскованих колонок.
- **Інваріант реєстру** (`tests/test_pii.py`): кожен модуль `tools/*` із
  mask-aware formatter має передавати `config.mask_pii` зі `server.py` —
  новий канал ПДн без маскування «зламає» тест, а не тихо витікне.

## Промпти (11)

Крім тулів сервер реєструє 11 MCP-промптів (`prompts.py:register`; джерело ідей — [feenlace/mcp-1c](https://github.com/feenlace/mcp-1c)) — готові покрокові інструкції для типових
задач розробки 1С, що спираються на тули вище. Кожен промпт повертає одне
користувацьке повідомлення (звичайний текст із планом дій), MCP-клієнт
підставляє його в діалог з моделлю.

| Промпт | Аргументи | Що дає |
|---|---|---|
| `review_module` | `object_type`, `object_name` | Ревʼю коду модуля об'єкта: помилки, порушення стандартів 1С, продуктивність (запити в циклі), читаність (зарезервовані слова як імена), робота з транзакціями/блокуваннями |
| `write_posting` | `document_name` | Допомога з написанням `ОбработкаПроведения(Отказ, РежимПроведения)`: рухи по регістрах, запит з’єднань по табличній частині, контроль залишків в оперативному режимі |
| `optimize_query` | `query` | Аналіз і оптимізація запиту: `LEFT`/`INNER JOIN`, індекси, віртуальні таблиці з параметрами замість вкладених запитів, `РАЗЛИЧНЫЕ`/`ПЕРВЫЕ`/`СГРУППИРОВАТЬ`, пакетні запити |
| `explain_config` | — | Пояснення структури поточної конфігурації: підсистеми, довідники, документи, регістри, плани рахунків, звіти/обробки, ролі, архітектура предметної області |
| `analyze_error` | `error_text` | Визначення типу помилки 1С (синтаксична / часу виконання / запиту / блокування / прав доступу), причина, спосіб виправлення, профілактика |
| `find_duplicates` | `object_type`, `object_name` | Пошук дублювального/надлишкового коду в модулях об'єкта: copy-paste, схожі процедури, повторювані запити, кандидати на винесення в загальний модуль |
| `write_report` | `description` | Допомога з написанням звіту: текст запиту для СКД, структура налаштувань (групування, поля, відбори, умовне оформлення), код модуля звіту |
| `explain_object` | `object_type`, `object_name` | Пояснення призначення й устрою об'єкта: реквізити, табличні частини, зв'язки з іншими об'єктами (посилальні типи), бізнес-логіка модулів |
| `baf_query_syntax` | — | Шпаргалка синтаксису запитів 1С: іменування таблиць в однині, віртуальні таблиці регістрів, робота з переліками через `ЗНАЧЕНИЕ()`, типові помилки з прикладами |
| `baf_metadata_navigation` | — | Порядок дослідження незнайомої конфігурації (`get_configuration_info` → `get_metadata_tree` без фільтра → з фільтром → `get_object_structure`), маппінг категорій метаданих на імена таблиц запитів |
| `baf_development_workflow` | `task` | Покроковий workflow розробки під конкретну задачу + чекліст перед написанням коду + повний список зарезервованих слів BSL (рос./англ.) |
